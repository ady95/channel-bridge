# 다자간(1:N) 연결을 고려한 설계 고도화

> 상태: **제안**. 아직 구현하지 않았다.
> 대상 커밋: `c24e369`
> 작성 근거: 코드 정독 + 1:1 구성에서의 실측. **3자 이상 구성은 실측되지 않았다.**

## 0. 요약

1:N 은 **설정상 이미 가능하다.** 한 브릿지에 Endpoint 를 3개 이상 넣으면 된다.
그러나 코드를 정독한 결과, 제대로 쓰려면 고쳐야 할 것이 둘 있다.

| # | 문제 | 심각도 | 범위 |
|---|---|---|---|
| 1 | 부분 실패 재시도가 **중복 전달**을 만든다 | 정합성 결함 | 파일과 무관 |
| 2 | 첨부가 대상 수만큼 **반복 다운로드**된다 | 성능·비용 | 파일 |

1번이 먼저다. 파일과 무관하며 데이터 정합성 문제다.

## 1. 현재 1:N 지원 수준

팬아웃은 이미 N 자를 전제로 쓰여 있다.

- [`config.py:165`](src/chbridge/config.py#L165) — Endpoint 제약이 `< 2` 다. `!= 2` 가 아니다.
- [`router.py:68`](src/chbridge/router.py#L68) — `targets()` 가 자기 자신을 뺀 **전체**를 돌려준다.
- `message_links` 는 `group_id` 하나에 행 N 개를 매다는 구조다. 참여 채널 수 제한이 없다.

중복 전달도 구조적으로 막혀 있다. A→B, A→C 로 복제된 뒤 B·C 의 자기 발신
이벤트가 돌아오지만, LoopGuard 방어 ② 가 이를 Replica 로 판정해 폐기한다.
따라서 C 는 A 에서 한 번만 받고 B 를 거쳐 다시 받지 않는다.

### 제약: 한 채널은 하나의 브릿지에만

[`config.py`](src/chbridge/config.py) 의 토폴로지 검증이 이를 강제한다.
`A↔B` 와 `B↔C` 를 별도 브릿지로 두어 메시를 만드는 것은 **금지**된다.
3자 이상은 반드시 **하나의 브릿지**에 모든 채널을 넣어야 한다.

```yaml
bridges:
  - id: three-way
    name: MM-A <-> MM-B <-> Slack
    endpoints:
      - { workspace: mm-a, team: bridge, channel: notice }
      - { workspace: mm-b, team: bridge, channel: notice }
      - { workspace: slack-dev, channel_id: C0XXXXXXXXX }
```

## 2. 결함 — 부분 실패 재시도가 중복을 만든다

### 현상

[`relay.py:90-113`](src/chbridge/relay.py#L90-L113) 의 팬아웃 루프에는 **대상별
멱등 가드가 없다.**

```python
group_id = await self._links.record_origin(...)      # 멱등 (links.py:149)
for target in targets:
    parent_id = await self._resolve_parent(...)      # ← 던질 수 있다
    new_id = await self._send_with_files(...)        # ← 던질 수 있다
    await self._links.record_replica(...)
```

[`worker.py:137`](src/chbridge/worker.py#L137) 은 실패 시 `relay.handle(event)`
**전체**를 다시 실행한다. 부분 진행 상태를 기억하지 않는다.

### 재현 조건

대상 3개 중 3번째에서 `ParentNotMappedError`(쓰레드 부모 미매핑), 레이트 리밋,
일시적 어댑터 오류 중 하나가 발생하면 → 재시도 때 루프가 처음부터 다시 돌고
→ **이미 전달된 1·2번 대상에 사본이 하나 더 생긴다.**

`ParentNotMappedError` 는 `retryable=True` 라 특히 걸리기 쉽다. 답글이 부모보다
먼저 처리되는 순간 발생하며, 이는 정상 동작 중에도 일어난다.

### 왜 1:1 에서는 드러나지 않았나

대상이 하나뿐이면 "실패 = 아무것도 전달되지 않음" 이므로 재시도가 깨끗하다.
**N≥2 에서만 나타나는 결함이다.** 그래서 지금까지의 1:1 실측으로는 발견되지
않았다.

### 수정안

필요한 조회 함수가 이미 있다 — [`links.py:118`](src/chbridge/store/links.py#L118)
의 `replica_in()` 은 `_on_edited`/`_on_deleted` 가 쓰던 것이다.

```python
for target in targets:
    if await self._links.replica_in(group_id, endpoint_ref=target.ref()) is not None:
        continue                      # 이 대상은 이미 전달됨. 건너뛴다.
    ...
```

`record_origin` 이 이미 멱등이므로 이 한 조건이면 팬아웃 전체가 재시도
안전해진다. 전달 보장은 "대상별 at-least-once + 중복 제거" 가 된다.

**비용**: 대상당 SELECT 1회 추가. 핫패스지만 인덱스가 있는 조회다.

## 3. 첨부 — N배 비용

### 현상

[`relay.py:196`](src/chbridge/relay.py#L196) 의 `_transfer_files` 가 대상별로
호출되고, 그 안에서 매번 원본을 연다 —
[`relay.py:236`](src/chbridge/relay.py#L236) 의 `async with src.open_file(file)`.

| 항목 | 대상 N개일 때 | 비고 |
|---|---|---|
| 원본 다운로드 | **N회** | 같은 바이트를 N번 |
| 대상 업로드 | N회 | 불가피 — 플랫폼이 다름 |
| 지연 | **Σ(대상별 전송시간)** | 루프가 직렬 |
| 원본 레이트 리밋 | N배 소모 | Slack 은 특히 민감 |

100MB 파일을 3자에 보내면 원본에서 200MB 를 더 받고 전송 시간이 3배가 된다.

### 검토한 방안

**A. 대상 병렬화만 (`asyncio.gather`)**
- 지연이 Σ → max 로 감소
- **대역폭은 그대로 N배**
- 변경량 최소

**B. 소스 1회 읽기 + tee 팬아웃**
- 대역폭·지연 모두 해결
- **가장 느린 대상이 전체를 붙잡는다.** Slack 업로드가 느리면 MM 업로드도
  같이 느려진다 (백프레셔 결합)
- 스트림 중간에 한 대상만 실패했을 때의 처리가 복잡

**C. 임시 파일로 1회 스풀 → N회 독립 업로드**  ← **권장**
- 다운로드 1회
- 업로드가 서로 독립 → **한 대상의 지연·실패가 다른 대상을 막지 않는다**
- 대상 병렬화가 자연스럽게 따라온다
- 대가: 임시 디스크 사용, 정리 책임

### 권장: N==1 직결 / N≥2 스풀 하이브리드

- **N==1** — 지금과 동일하게 원본에서 대상으로 직결 스트리밍. 스풀하지 않는다.
  기존 1:1 동작에 회귀가 없다.
- **N≥2** — 스풀 후 대상별 독립 업로드.

임시 사용량은 `(동시 전달 건수 × 파일 크기)` 로 묶인다. 상한을 설정값으로 두고
초과하면 직결 스트리밍으로 되돌린다 (N배 대역폭을 감수).

### 어댑터 계약 변경은 필요 없다

`upload_file` 이 이미 `AsyncIterator[bytes]` 를 받으므로 파일에서 읽어 먹이면
된다. **변경은 Relay 안에서 끝난다.** `FileMode`(PRE_UPLOAD / POST_ATTACH) 분기도
그대로 유지된다.

### 구조 재배치

첨부 처리가 지금은 대상 루프 **안**에 있다. 이를 루프 **위**로 올려야 한다.

```python
async def _on_created(...):
    group_id = await self._links.record_origin(...)
    async with self._spool(src, event.files, fanout=len(targets)) as blobs:
        # N==1 이면 blobs 는 원본 직결 핸들, N>=2 면 임시 파일 핸들
        for target in targets:                       # 이후 gather 로 병렬화
            if await self._links.replica_in(...) is not None:
                continue
            await self._send_one(target, blobs)      # PRE/POST 분기는 그대로
```

정리 책임이 생긴다. 정상 종료·예외·취소 모든 경로에서 임시 파일이 지워져야
한다. `_release()` 때와 같은 종류의 문제다.

## 4. 정직하게 남길 트레이드오프

이 변경은 지금까지 장점으로 내세운 **"바이트는 브릿지를 통과만 하고 어디에도
저장되지 않는다"** 를 부분적으로 포기하는 것이다.

1:1 에서는 그 성질이 공짜였다. 1:N 에서는 그 대가가 N배 대역폭으로 나타난다.
둘 다 가질 수는 없다. 하이브리드는 "공짜인 구간에서만 공짜를 유지한다" 는
타협이다.

## 5. 그 밖에 1:N 에서 확인이 필요한 것

- **크기 상한이 대상마다 다르다.** MM(100MB) + Slack(1GB) 3자 구성에서 300MB
  파일은 Slack 에는 전달되고 MM 에는 안내 문구가 된다. 대상별 판정이므로
  동작은 맞지만, 의도한 결과인지 확인이 필요하다.
- **쓰레드 부모 매핑은 구조상 3자에서도 맞다** (`replica_in` 이 대상별 조회).
  다만 **실측된 적이 없다.**
- **Slack 레이트 게이트는 채널당**이므로 서로 다른 채널인 대상끼리는 경합하지
  않는다. 병렬화해도 안전하다.
- **삭제 시 `delete_group`** 이 그룹 전체를 지운다. 대상 일부만 삭제에 실패한
  상황에서의 동작을 3자에서 확인해야 한다.
